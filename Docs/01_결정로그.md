# 결정 로그 (확정된 규칙 모음)

> 이 문서는 **확정된 규칙의 기준**이다. 코드와 충돌하면 임의로 판단하지 말고 사용자에게 알린다.
> 최종 갱신: 2026-11-25 / 현재 단계: **Phase 4-A·4-B 완료(자동 테스트 통과, 수동 테스트: Phase 5에서 4-A·4-B 함께 진행), Phase 5 대기**

**상태 표기**
- `[구현·통과]` 코드에 반영되었고 테스트를 통과함
- `[구현·대기]` 코드에 반영되었으나 사용자 테스트 결과를 아직 받지 못함
- `[확정·미구현]` 규칙은 확정되었고 아직 코드가 없음
- `[임시]` 검증용 임시 처리. 나중에 교체 예정
- `[미결]` 아직 정해지지 않음 (→ 05_로드맵과_미결사항.md 참고)

## 1. 프로젝트 기본

- 엔진/언어: Unity 6.2, C#. 1인 개발자(초보), 바이브 코딩, 0원 테스트 플랜 (무료 에셋·도구 우선, 유료 플러그인 금지)
- 장르: 턴제 로그라이크. Slay the Spire식 카드 전투 + Into the Breach식 적 행동 예고
- 핵심 정체성: **수학 공식과 기호가 실제 공격·전투 전략의 수단**이 되는 게임. 카드 이미지에 공식을 표시하는 데 그치지 않고, 수학적 연산과 개념이 실제 효과에 영향을 준다. (예: 곱셈 연산 피해 증폭, 방정식 조건 충족 시 발동하는 특수 공격)
- 수학을 몰라도 즐길 수 있어야 한다. 수학 지식은 필수 조건이 아니다.
- 수학 범위 확장 계획: 초반 사칙연산·기본 기호 → 중반 대수·일차방정식·연립방정식 → 후반 함수·직선의 기울기·그래프 → 장기 미분·적분·푸리에 급수
- 현재 Strike, Guard, HeavyStrike, QuickJab 등은 **전투 시스템 검증용 임시 카드**이다. 최종 카드가 아니다.

## 2. 팀과 작업 방식

- Claude: C# 스크립트와 시스템 로직 구현 / ChatGPT: 기획·시스템 규칙·데이터 구조·밸런스 / Gemini: QA·오류 분석·전체 조율
- 입력은 `[현재 개발 목표]`와 `[ChatGPT가 확정한 기획 명세]` 형태로 온다.
- **Phase 번호(확정)**: Phase 1 기본 전투 / Phase 2 CardInstance·카드 강화 / Phase 3 카드 대상 선택·전투 효과 확장 / Phase 4 Buff·Special (4-A 상태 효과·플레이어 Buff 카드·재정렬 / 4-B 적 SelfBuff·AllyBuff·AllyHeal, 4-A 완료 후 4-B 진입) / Phase 5 전투 UI 프로토타입. 적 콘텐츠 중심의 별도 Phase 번호는 쓰지 않는다.
- **작업 흐름(2026-11-23~)**: claude.ai 채팅 = 기획 확인·ChatGPT 질문 정리·구현 전 분석·코드 검토 / Rider의 Claude Code = 실제 코드 수정·Editor.log 확인 / 사용자 = Unity 테스트·커밋·푸시. 문서의 기준 위치는 저장소 `Docs/` 폴더
- **문서 갱신(2026-11-23 사용자 승인)**: 각 단계가 끝나고 사용자가 테스트 통과를 알려 주면 Claude Code가 Docs의 01, 02, 05를 갱신한다. 01에는 ChatGPT 확정안과 사용자가 승인한 내용만 적는다. 03, 04는 수정하지 않는다.
- 단계별 구현. 각 단계 종료 시 **변경된 파일 목록, 테스트 방법, 기대 결과, 남은 문제**를 보고하고 사용자 테스트 결과 확인 후 다음 단계로 간다.
- 완료 보고는 **변경 파일 / 신규 파일 / 구현 내용 / 자동 테스트 / 회귀 테스트 / 수동 테스트 / 미해결 문제**로 구분한다. 테스트하지 않은 항목은 **NOT TESTED**로 표기한다.
- 구현 전에 **변경 대상 스크립트, 기존 흐름에 미치는 영향, 데이터 연결 방식, 처리 구조, 회귀 테스트 영향**을 분석해 보고하고 승인을 받는다.
- 기획을 임의로 바꾸지 않는다. 제안과 구현을 구분한다.
- 기존 코드를 크게 바꿔야 하면 **코드를 쓰기 전에** 변경 이유와 영향을 설명하고 승인을 받는다. 기존 구조를 최대한 유지하고 불필요한 재작성은 피한다.
- 기존 통과 테스트를 깨지 않는다. 큰 변경 후 회귀 테스트 기준값을 알려 준다.
- Unity 컴파일을 Claude가 직접 할 수 없으므로 컴파일 에러·콘솔 로그를 근거로 수정한다.
- 코드 원칙: 단순한 컴포넌트형 C#, 친절한 주석, 수치는 인스펙터/ScriptableObject, UI와 로직 느슨한 결합, 새 공식·카드 추가 시 기존 코드를 크게 수정하지 않는 구조
- MVP 범위 밖의 UI 연출·에셋 생성 코드는 넣지 않는다.

## 3. 전투 규칙

### 3-1. 플레이어 초기값 (인스펙터 값) `[구현·통과]`
- 최대 체력 70 (시작 체력 = 최대 체력), 최대 에너지 3, 전투 시작 방어도 0
- 턴 시작 드로우 5장, 손패 최대 10장
- 전투가 끝나도 체력은 **자동 회복되지 않는다.** 체력 초기화는 런 시작 때만 한다.

### 3-2. 턴 진행 순서 (확정) `[구현·통과]`
플레이어 선공.
1. 플레이어 턴 시작
2. 플레이어 방어도 초기화
3. 에너지 최대치까지 회복
4. 카드 5장 드로우
5. 카드/스킬 사용
6. 플레이어 턴 종료 (**수동**)
7. 남은 에너지 소멸, 남은 손패 전부 버림 더미로
8. 적 턴: 살아 있는 적이 **리스트 순서대로** 행동 (적마다 방어도 초기화 → 행동 실행)
9. 다음 플레이어 턴 시작

### 3-3. 에너지 `[구현·통과]`
- 턴 시작 시 최대치까지 회복, 턴 종료 시 남은 에너지 소멸
- 카드와 스킬은 **같은 에너지**를 쓴다. 에너지가 부족하면 사용 불가
- 최대 에너지는 카드·유물 효과로 증가 가능. **증가해도 현재 에너지는 즉시 늘지 않고, 다음 플레이어 턴 시작부터 새 최대치로 회복한다.**
- 자동 턴 종료는 **MVP에 없다**(수동만). **에너지가 0이어도 자동으로 턴을 종료하지 않는다.** 추후 추가 시 "사용 가능한 0코스트 카드가 손에 있으면 사용 기회를 유지"한다. `[확정·미구현]`

### 3-4. 방어도와 체력 `[구현·통과]`
- 피해는 방어도를 먼저 깎고, 막지 못한 피해만 체력에 적용
- 체력은 0 아래로 내려가지 않음. 회복은 최대 체력을 넘지 못함. 0 이하의 피해·방어도·회복 값은 무시
- **플레이어 방어도: 다음 플레이어 턴이 시작될 때 초기화** (적 턴 동안은 유지되어 적 공격을 막는다)
- **적 방어도: 해당 적의 행동이 시작되기 직전에 초기화.** 따라서 적이 방어 행동으로 얻은 방어도는 플레이어 턴 동안 유지되어 플레이어 공격을 막는다.

### 3-5. 승패와 전투 종료 `[구현·통과]`
- 적 체력 0 이하 → 즉시 제거. 제거된 적은 이후 행동하지 않음
- 모든 적 처치 → 플레이어 턴이 남아 있어도 **즉시 승리** (전체 공격은 모든 대상 처리 후 한 번 판정, 7-4)
- 플레이어 체력 0 이하 → **즉시 패배**. 남은 적은 행동하지 않음
- 전투 종료 후 카드 사용·턴 종료 등 추가 행동과 카드 효과는 실행되지 않음
- 전투 종료(승리·패배) 시 플레이어와 모든 적의 상태 효과(버프/디버프)를 제거한다 `[구현·통과]` (Phase 4-A)

## 4. 카드 규칙

### 4-1. 카드 종류와 사용 `[구현·통과]`
- `CardType`: **Attack / Defend / Buff / Special** (4종, Buff는 별도 유형으로 확정)
- 카드 비용 0~5 에너지. 카드 등급: 일반/희귀/전설 (등급 데이터는 이후 단계에서 추가)
- 카드 사용 순서: **에너지 확인 및 지불 → 효과 적용 → 버림 더미 이동**
- 사용 실패(에너지 부족, 잘못된 손패 번호, 대상 없는 공격, 공격 카드의 Self 대상, 효과가 None인 Buff 카드, 적 대상인데 대상이 없는 Buff 카드)이면 에너지도 카드도 그대로
- **Buff / Special 카드는 Phase 4-A에서 구현됨** (이전의 "미구현 카드 사용 실패" 처리는 삭제) `[구현·통과]`
- 모든 카드는 사용 후 버림 더미로 간다. **카드 소멸 시스템은 MVP에 없다**(추후 확장).
- 카드의 대상 유형은 `targetType`으로 명시한다 (→ 7장).

### 4-2. 덱·더미 규칙 `[구현·통과]`
- 전투 시작 시: 런 덱 전체 → 뽑기 더미 → 셔플 → 손패 초기화 → 버림 더미 초기화 (전투마다 새로 섞음)
- 드로우 중 뽑기 더미가 비면 버림 더미를 **즉시 셔플해 새 뽑기 더미**로 만들고 드로우를 이어감. 두 더미가 모두 비면 드로우 중단
- 손패가 10장이면 추가 드로우 카드는 **뽑기 더미에서 소모되어 즉시 버림 더미로** 이동 (슬레이 더 스파이어 방식). 같은 드로우 과정에서 재셔플로 되돌아오지 않고, 다음 드로우부터는 일반 카드로 취급
- 시작 덱 10장: **공격 5, 방어 4, 특수 1**

### 4-3. 카드 강화 `[구현·통과]`
- 구조: `CardData`(원본 에셋) / `CardInstance`(덱에 있는 카드 한 장의 상태)
- 같은 카드가 여러 장이어도 **한 장만** 강화 가능. 카드 한 장당 강화는 **1회**
- 강화 수치는 **카드마다 개별 설정**(`upgradedValue`). **강화 가능 판정 = `upgradedValue > value`** (강화가 없는 카드는 `upgradedValue`를 `value`와 같게 둠)
- **강화해도 비용과 대상 유형은 변하지 않는다.** 강화는 기본 수치만 올린다.
- **원본 `CardData` 에셋은 절대 수정하지 않는다.**
- 강화 상태는 현재 런 동안 유지(전투를 넘어서 유지)되고, 새 런 시작 시 초기화
- 강화는 **휴식 노드**에서 "체력 회복 vs 카드 강화" 중 하나를 선택하는 방식. **MVP에서는 상점에서 카드 강화를 제공하지 않는다.**
- 덱 구조: `startingDeck`(인스펙터의 기본 덱 구성) + `runDeck`(현재 런의 `CardInstance` 목록). 새 런을 시작하면 `startingDeck` 기준으로 `runDeck`을 재생성. 런 시작 진입점은 `CombatManager.StartRun()`
- 테스트용 강화 수치(임시, 최종 밸런스 아님): 타격 6→9, 수비 5→8, 강타 10→14, 속공 2→4

### 4-4. 시작 덱의 특수 카드 `[구현·통과]` (Phase 4-A)
- 이름: **재정렬** / 종류: Special / 대상: Self / 비용: 1
- 기본 효과: **카드 2장 드로우**, 강화 효과: **카드 3장 드로우**, 강화 시 비용 변화 없음
- 손패 최대 10장, 뽑기 더미 소진 시 재셔플 규칙은 기존과 동일
- 구현 방식: 카드의 `value`를 드로우 장수로 사용 (기본 2, `upgradedValue` 3)
- **카드 사용 순서(효과 → 버림)를 그대로 유지한다** (사용자 승인). 재정렬 카드가 손패에 남아 있는 상태에서 드로우하므로, 손패가 10장일 때 쓰면 뽑은 카드는 버림 더미로 간다.
- Special 효과 종류를 구분하는 필드는 **추가하지 않는다** (사용자 승인). 지금은 Special = value만큼 드로우. 다른 Special 카드가 생기면 그때 결정한다.

### 4-5. Buff 카드 `[구현·통과]` (Phase 4-A)
- `CardData`에 `statusEffect`(효과 종류)와 `duration`(지속시간) 추가. 효과 수치는 기존 `value` / `upgradedValue`를 사용한다.
- 적용 대상은 `targetType`으로 지정: Self / SingleEnemy / AllEnemies / RandomEnemy (대상 결정 규칙은 7장과 같음)
- **강화 시 보정 수치만 증가하고 지속시간은 증가하지 않는다.**
- 감소 효과 카드도 `value`는 양수로 넣는다 (예: 공격력 감소 2 → value 2). 부호는 효과 종류가 정한다.
- 테스트용 Buff 카드 (모두 Buff / Cost 1 / Duration 2 / 시작 덱 미포함, 최종 밸런스 아님):

| 카드 | 대상 | 효과 | 기본 | 강화 |
|---|---|---|---:|---:|
| 집중 | Self | 공격력 증가 | +2 | +3 |
| 약화 | SingleEnemy | 공격력 감소 | -2 | -3 |
| 견고 | Self | 방어도 증가 | +2 | +3 |
| 균열 | SingleEnemy | 방어도 감소 | -2 | -3 |

- 자동 테스트(`StatusEffectTest`)가 코드 안에서 임시로 만든다. 에셋은 수동 테스트할 때만 만들어 시작 덱에 잠시 넣는다.
- **Phase 4-A 수동 테스트는 UI가 없어 Phase 5(전투 UI 프로토타입)에서 4-A·4-B 함께 진행한다** (사용자 승인, 2026-11-25).

## 5. 적 규칙

### 5-1. 행동 예고와 순서 `[구현·통과]`
- 적마다 고유 행동 패턴을 가지며 순서대로 반복(순환)
- 일반 적: 다음 행동 1개 예고 / 엘리트: 다음 행동 및 특수 조건 예고 / 보스: 여러 턴 행동 패턴 예고
- **예고와 실제 실행은 항상 일치**해야 한다 (같은 데이터를 사용)
- **상태 효과를 반영한 최종 수치를 예고한다** `[구현·통과]` (Phase 4-A). 표기에는 효과 종류 이름을 쓴다 (사용자 승인). 예: `공격 5 (기본 7, 공격력 감소 -2)`. 보정이 없으면 `공격 7`처럼 기존 표기 그대로. 효과가 걸리거나 갱신·만료되면 예고를 다시 계산한다.
- 적 행동 순서: 화면 왼쪽부터 오른쪽. **UI가 없는 동안은 리스트 순서 = 왼쪽부터**이며, UI 구현 후에도 이 순서를 유지한다.
- 적 회복은 최대 체력을 초과할 수 없다.

### 5-2. 적 행동 종류 `[구현·통과]` (Phase 4-B, 2026-11-25)
- **Attack / Defend / SelfBuff / AllyBuff / AllyHeal** 5종 (ChatGPT 4-B 지시서)
  - SelfBuff: 자기 자신의 공격력 +2, 지속시간 2턴
  - AllyBuff: **자기 자신을 제외한 살아 있는 아군 중 가장 왼쪽**에게 공격력 +2, 지속시간 2턴. 대상의 지속시간은 대상 자신의 행동 종료 시 감소 (기존 규칙 유지)
  - AllyHeal: **자기 자신을 제외한 살아 있는 아군 중 체력이 감소한 적의 가장 왼쪽**을 HP 6 회복. 최대 체력 초과 불가. 체력이 가득 찬 아군은 대상이 아니다
  - **대상이 없으면 그 행동을 생략한다.** 생략해도 그 행동 차례는 소비한다 (방어도 초기화·지속시간 감소·다음 행동으로 이동은 평소대로)
  - 수치는 모두 임시 테스트 수치. 효과 종류·수치·지속시간은 `EnemyActionData`의 `statusEffect` / `value` / `duration` (Inspector 값)
- 행동 예고 문구: `자기 강화: 공격력 +2 (2턴)` / `아군 강화: 2번 슬라임 공격력 +2 (2턴)` / `아군 회복: 2번 슬라임 +6` / 대상 없음 `행동 없음(대상 없음)`
- **예고와 실제 실행은 같은 대상 선택 규칙을 쓰고, 실행 시점에 대상을 다시 고른다.** 예고는 전투 시작 후, 카드 사용 후(적 사망 포함), **적 하나가 행동할 때마다 살아 있는 모든 적**에 대해 다시 계산한다 (사용자 지시)
  - 알려진 한계: 같은 적 턴에 앞선 적의 행동 때문에 뒤 적의 대상이 바뀔 수 있다 (예: 회복으로 체력이 가득 참). 이때는 실행 시점에 다시 고른다 (사용자 승인)
- 테스트 적 (에셋 없이 자동 테스트 `EnemyBuffTest`가 임시로 만든다. 정식 콘텐츠·시작 구성에 넣지 않는다. 씬의 적 구성은 슬라임 2마리 그대로):
  - 주술사: 최대 체력 30, SelfBuff → Attack 4 → AllyBuff → AllyHeal 반복
  - 아군 테스트 적: 최대 체력 20, 공격 5

## 6. 버프·디버프 `[구현·통과]` (Phase 4-A 2026-11-23, 4-B 2026-11-25)

초기 MVP 효과 4종: **공격력 증가(AttackUp) / 공격력 감소(AttackDown) / 방어도 증가(DefenseUp) / 방어도 감소(DefenseDown)**

### 6-1. 계산
- 최종 피해량 = **Max(0, 기본 피해량 + 공격력 보정)**
- 최종 방어도 = **Max(0, 기본 방어도 + 방어도 보정)**
- 플레이어와 적 모두 같은 계산 규칙을 적용한다.
- **보정은 "그 효과를 가진 쪽"의 공격·방어에 적용한다** (사용자 승인). 피해를 받는 쪽의 효과는 받는 피해량에 영향을 주지 않는다.
  - 공격력 증가 → 플레이어 공격 카드 피해 / 공격력 감소 → 적 공격 행동 피해 / 방어도 증가 → 플레이어 방어 카드 / 방어도 감소 → 적 방어 행동의 방어도 획득량 (Phase 4-A 범위)
- 전체 공격은 적마다 개별 보정, 무작위 공격은 선정된 적에게 보정한다.
- 반대 효과(증가/감소)는 독립적으로 유지하고 최종 계산에서 합산

### 6-2. 재적용 (Phase 4-B에서 변경, 2026-11-25)
- 같은 효과를 다시 걸면 **수치는 중첩하지 않는다. 기존 효과의 수치를 유지하고 지속시간만 새 값으로 갱신**한다 (ChatGPT 4-B 지시서, 통합 기획서 기존 규칙 우선). 반대 효과는 독립적으로 유지한다.
  - 예: 기존 공격력 +2 (1턴)에 공격력 +3 (2턴) 적용 → 결과 공격력 +2 (2턴)
  - 4-A 때 승인한 "더 큰 수치 유지" 규칙은 **이 규칙으로 대체되었다** (사용자 승인). 플레이어 Buff 카드에도 같이 적용된다.
- 수치나 지속시간이 **0 이하인 효과는 걸지 않는다** (사용자 승인, 기존 "0 이하 값은 무시" 규칙과 맞춤). 이 경우에도 카드 사용 자체는 성공으로 처리한다.

### 6-3. 지속시간
- 턴 단위. **플레이어 효과: 플레이어 턴 종료 시 감소 / 적 효과: 해당 적의 행동 종료 시 감소**
- 지속시간이 0이 되면 제거. 전투 종료 시 모두 제거
- **2턴 = 효과가 적용되는 턴을 포함해 두 번 적용.** 플레이어 카드는 사용한 턴을 포함해 2턴
- **자기 행동 중에 자기 자신에게 건 효과는 그 행동이 끝날 때 지속시간을 줄이지 않는다.** 새로 건 경우와 지속시간을 갱신한 경우 모두 해당하며, 이미 걸려 있던 다른 효과는 평소처럼 줄어든다 (사용자 승인) `[구현·통과]` (Phase 4-B)
  - 예: 적 SelfBuff 공격력 +2 (2턴) → 그 행동 끝 2턴 그대로 → 다음 행동(공격에 +2 반영) 끝 1 → 그다음 행동 끝 만료

### 6-4. 확인 방법
- 전투 로그에 효과 적용·갱신·만료를 기록한다 (`[효과]` 로그)
- Inspector: Player / Enemy 오브젝트의 Combatant → Status Effects 목록에서 효과 종류·수치·남은 턴 확인
- 초기 테스트 수치: 효과 ±2, 지속시간 2턴. Buff 카드는 카드 에셋 인스펙터, 적 행동은 EnemyData의 행동 패턴 인스펙터에서 변경 가능

## 7. 카드 대상 선택 `[구현·통과]` (Phase 3, 2026-11-23)

### 7-1. targetType
- `CardData`에 `targetType` 필드. enum: **SingleEnemy / AllEnemies / RandomEnemy / Self**
- 각 카드는 대상 유형을 **명시적으로** 지정한다. 방어 및 자기 강화 카드는 **Self** (수비·재정렬 에셋 = Self)
- **공격 카드의 Self 대상 공격은 허용하지 않는다** (사용 실패, 에너지·카드 그대로)
- 방어 카드의 targetType이 Self가 아니면(데이터 실수) **경고 로그 후 자신에게 적용**
- 기존 타격·강타·속공은 모두 **SingleEnemy**

### 7-2. 단일 공격 (SingleEnemy)
- 플레이어가 적을 직접 선택한다. 선택 상태는 `CombatManager.selectedEnemyIndex` (칸 번호, -1 = 선택 없음)
- 임시 키보드 조작(UI 전): **← / → = 대상 변경(끝에서 멈춤), Tab = 다음 살아 있는 적(끝에서 처음으로 순환), 1~9·0 = 카드 사용, Space = 턴 종료**
- **전투 시작 시 기본 대상 = 가장 왼쪽의 살아 있는 적**
- 살아 있는 적이 한 마리뿐이면 자동 선택
- 선택된 적이 죽으면 **죽은 적 위치와 무관하게 가장 왼쪽의 살아 있는 적**으로 자동 변경
- 대상이 없으면 선택을 해제한다
- UI는 `SelectEnemy(칸)`, `SelectNextEnemy()`, `SelectPreviousEnemy()`, `SelectNextEnemyLoop()`를 호출한다

### 7-3. 적 번호
- 처음 배치된 위치(Enemies 리스트 칸) 기준의 **고정 번호**. 적이 사망해도 남은 적의 번호는 바뀌지 않는다

### 7-4. 전체 공격 (AllEnemies)
- 왼쪽부터 오른쪽 순서로 피해 적용, 에너지는 한 번만 지불
- HP 0 이하인 적은 제거하고, 나머지 적에게 계속 피해 적용 (구현: 모든 대상에 피해를 준 직후 사망 적 일괄 제거. 처치 시 발동 효과가 생기면 루프 안 제거로 변경)
- **전체 대상 처리가 끝난 뒤 승리 여부를 한 번 판정**한다. 적 제거와 전투 종료 판정을 구분한다

### 7-5. 무작위 공격 (RandomEnemy)
- 카드 한 장당 살아 있는 적 중 **무작위 1명, 1회 공격**
- **카드 사용 순간** 대상을 결정한다. 사전 대상 예고 없음
- 실제 선택된 대상은 전투 로그에 표시한다
- **다중 타격은 Phase 3 범위에서 제외**

### 7-6. 테스트 전용 카드 (최종 밸런스 아님, 시작 덱에 넣지 않음)
| 이름 | Type | TargetType | Cost | Value | UpgradedValue |
|---|---|---|---|---|---|
| 휩쓸기 | Attack | AllEnemies | 1 | 4 | 6 |
| 난사 | Attack | RandomEnemy | 1 | 7 | 10 |
- 자동 테스트(`TargetSelectionTest`)가 코드 안에서 임시로 만든다. 에셋은 수동 테스트할 때만 만들어 시작 덱에 잠시 넣는다.

## 8. 로그라이크 진행 (명세, 대부분 미구현)

- 3개 구역 + 최종 보스. 각 구역은 분기형 맵, 구역 마지막에 구역 보스
- 노드 종류: 일반 전투, 엘리트, 상점, 휴식, 이벤트, 보스
- **런 종료 시 초기화**: 체력, 골드, 카드, 유물, 임시 강화 / **유지**: 도감·영구 콘텐츠 해금 기록
- 영구 능력치 강화 시스템은 없다.
- 영구 데이터와 런 단위 데이터는 반드시 분리한다. (영구 저장 시스템은 미구현)

### 보상 (Phase 5 이후)
- 전투 승리 후 **카드 보상 또는 골드 보상 중 하나** 선택
- 카드 보상: 무작위 카드 3장 중 1장 선택. 등급 확률 **일반 70% / 희귀 25% / 전설 5%**
- 카드 풀 구성, 골드 획득량, 상점 가격, **보상 건너뛰기 여부는 해당 단계 진입 전에 다시 결정** `[미결]`

### 상점
- 카드 구매, 유물 구매, 카드 제거(현재 런에서 복구 불가). 구매한 상품은 상점에서 제거, 퇴장 후 재방문 불가, 골드 부족 시 구매 불가

## 9. 스킬·유물 (명세, 미구현)

- 스킬: 별도 슬롯에 장착, **초기 슬롯 2개**, 카드와 같은 에너지 사용, 에너지가 충분하면 반복 사용 가능, 전투 중 교체 불가, 전투 승리 후 장착·교체 가능. 스킬은 보스·이벤트·특수 조건으로 획득. 영구 해금 스킬은 이후 런에서 획득 후보가 될 수 있음
- 유물: 패시브 중심, 보유 개수 제한 없음, 기본적으로 독립 작동, 일부 핵심 조합에만 시너지, 보스 처치 시 보스 전용 유물 1개 확정 획득, 런 종료 시 초기화, 도감 발견 기록은 영구 유지

## 10. 장기 방향 (UI·수학 시스템·도감)

- **UI**: Phase 1~4에서는 보류(Debug.Log와 인스펙터). **Phase 5에서 전투 UI 프로토타입** — 플레이어 체력·에너지 표시, 적 캐릭터와 체력 표시, 손패 카드 표시와 클릭으로 사용, 적 클릭으로 대상 선택, 턴 종료 버튼, 카드 효과·전투 상황 표시, 승리·패배 화면. 이후 메인 메뉴, 분기형 맵, 상점, 휴식, 유물, 도감 UI
- **UI 설계 원칙**: UI는 게임 로직의 함수를 호출하고 공개된 상태를 읽기만 한다. 로직은 UI를 알지 못한다.
- **수학 시스템**: 카드 데이터에 나중에 연결할 수 있도록 구조를 고려한다 — 수학적 분류(사칙연산·방정식·함수 등), 수학 기호·공식 표현, 카드의 실제 전투 효과, 카드 설명과 수학적 원리, 도감 등록 연결, 카드 강화와 수학적 효과의 관계. **복잡한 범용 효과 시스템을 미리 만들지 않고**, 실제 구현 단계에서 필요한 만큼 확장한다.
- **도감**: 획득한 수학 공식·기호를 확인하는 선택형 보조 시스템. 신규 공식 획득 시 등록, 간단한 설명과 활용법 제공, 전투 중에는 간략 설명 + "자세히 보기"로 도감 이동. **도감을 읽지 않아도 클리어 가능**해야 한다. 독립형(메인 메뉴/마을)과 전투 연동형을 섞은 A+B 방식
- 이후 Phase 계획에 **UI 프로토타입과 수학 공식 시스템을 반드시 포함**한다.
