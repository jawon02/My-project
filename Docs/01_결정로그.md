# 결정 로그 (확정된 규칙 모음)

> 이 문서는 **확정된 규칙의 기준**이다. 코드와 충돌하면 임의로 판단하지 말고 사용자에게 알린다.
> 최종 갱신: 2026-11-23 / 현재 단계: **Phase 2 구현 완료, 테스트 결과 대기**

**상태 표기**
- `[구현·통과]` 코드에 반영되었고 테스트를 통과함
- `[구현·대기]` 코드에 반영되었으나 사용자 테스트 결과를 아직 받지 못함
- `[확정·미구현]` 규칙은 확정되었고 아직 코드가 없음
- `[임시]` 검증용 임시 처리. 나중에 교체 예정
- `[미결]` 아직 정해지지 않음 (→ 05_로드맵과_미결사항.md 참고)

## 1. 프로젝트 기본

- 엔진/언어: Unity 6.2, C#. 1인 개발자(초보), 바이브 코딩, 0원 테스트 플랜 (무료 에셋·도구 우선, 유료 플러그인 금지)
- 장르: 턴제 로그라이크. Slay the Spire식 카드 전투 + Into the Breach식 적 행동 예고
- 핵심 정체성: **수학 공식과 기호가 실제 공격·전투 전략의 수단**이 되는 게임. 카드 이미지에 공식을 표시하는 데 그치지 않고, 수학적 연산과 개념이 실제 효과에 영향을 준다. (예: 곱셈 연산 피해 증폭, 방정식 조건 충족 시 발동하는 특수 공격)
- 수학을 몰라도 즐길 수 있어야 한다. 수학 지식은 필수 조건이 아니다.
- 수학 범위 확장 계획: 초반 사칙연산·기본 기호 → 중반 대수·일차방정식·연립방정식 → 후반 함수·직선의 기울기·그래프 → 장기 미분·적분·푸리에 급수
- 현재 Strike, Guard, HeavyStrike, QuickJab 등은 **전투 시스템 검증용 임시 카드**이다. 최종 카드가 아니다.

## 2. 팀과 작업 방식

- Claude: C# 스크립트와 시스템 로직 구현 / ChatGPT: 기획·시스템 규칙·데이터 구조·밸런스 / Gemini: QA·오류 분석·전체 조율
- 입력은 `[현재 개발 목표]`와 `[ChatGPT가 확정한 기획 명세]` 형태로 온다.
- 단계별 구현. 각 단계 종료 시 **변경된 파일 목록, 테스트 방법, 기대 결과, 남은 문제**를 보고하고 사용자 테스트 결과 확인 후 다음 단계로 간다.
- 기획을 임의로 바꾸지 않는다. 제안과 구현을 구분한다.
- 기존 코드를 크게 바꿔야 하면 **코드를 쓰기 전에** 변경 이유와 영향을 설명하고 승인을 받는다.
- 기존 통과 테스트를 깨지 않는다. 큰 변경 후 회귀 테스트 기준값을 알려 준다.
- Unity 컴파일을 Claude가 직접 할 수 없으므로 컴파일 에러·콘솔 로그를 근거로 수정한다.
- 코드 원칙: 단순한 컴포넌트형 C#, 친절한 주석, 수치는 인스펙터/ScriptableObject, UI와 로직 느슨한 결합, 새 공식·카드 추가 시 기존 코드를 크게 수정하지 않는 구조
- MVP 범위 밖의 UI 연출·에셋 생성 코드는 넣지 않는다.

## 3. 전투 규칙

### 3-1. 플레이어 초기값 (인스펙터 값) `[구현·통과]`
- 최대 체력 70 (시작 체력 = 최대 체력), 최대 에너지 3, 전투 시작 방어도 0
- 턴 시작 드로우 5장, 손패 최대 10장
- 전투가 끝나도 체력은 **자동 회복되지 않는다.** 체력 초기화는 런 시작 때만 한다.

### 3-2. 턴 진행 순서 (확정) `[구현·통과]`
플레이어 선공.
1. 플레이어 턴 시작
2. 플레이어 방어도 초기화
3. 에너지 최대치까지 회복
4. 카드 5장 드로우
5. 카드/스킬 사용
6. 플레이어 턴 종료 (**수동**)
7. 남은 에너지 소멸, 남은 손패 전부 버림 더미로
8. 적 턴: 살아 있는 적이 **리스트 순서대로** 행동 (적마다 방어도 초기화 → 행동 실행)
9. 다음 플레이어 턴 시작

### 3-3. 에너지 `[구현·통과]`
- 턴 시작 시 최대치까지 회복, 턴 종료 시 남은 에너지 소멸
- 카드와 스킬은 **같은 에너지**를 쓴다. 에너지가 부족하면 사용 불가
- 최대 에너지는 카드·유물 효과로 증가 가능. **증가해도 현재 에너지는 즉시 늘지 않고, 다음 플레이어 턴 시작부터 새 최대치로 회복한다.**
- 자동 턴 종료는 **MVP에 없다**(수동만). 추후 추가 시 "사용 가능한 0코스트 카드가 손에 있으면 사용 기회를 유지"한다. `[확정·미구현]`

### 3-4. 방어도와 체력 `[구현·통과]`
- 피해는 방어도를 먼저 깎고, 막지 못한 피해만 체력에 적용
- 체력은 0 아래로 내려가지 않음. 회복은 최대 체력을 넘지 못함. 0 이하의 피해·방어도·회복 값은 무시
- **플레이어 방어도: 다음 플레이어 턴이 시작될 때 초기화** (적 턴 동안은 유지되어 적 공격을 막는다)
- **적 방어도: 해당 적의 행동이 시작되기 직전에 초기화.** 따라서 적이 방어 행동으로 얻은 방어도는 플레이어 턴 동안 유지되어 플레이어 공격을 막는다.

### 3-5. 승패와 전투 종료 `[구현·통과]`
- 적 체력 0 이하 → 즉시 제거. 제거된 적은 이후 행동하지 않음
- 모든 적 처치 → 플레이어 턴이 남아 있어도 **즉시 승리**
- 플레이어 체력 0 이하 → **즉시 패배**. 남은 적은 행동하지 않음
- 전투 종료 후 카드 사용·턴 종료 등 추가 행동과 카드 효과는 실행되지 않음
- 전투 종료 시 임시 효과(버프/디버프) 제거 (버프 구현 시 적용)

## 4. 카드 규칙

### 4-1. 카드 종류와 사용 `[구현·통과]`
- `CardType`: **Attack / Defend / Buff / Special** (4종, Buff는 별도 유형으로 확정)
- 카드 비용 0~5 에너지. 카드 등급: 일반/희귀/전설 (등급 데이터는 Phase 5에서 추가)
- 카드 사용 순서: **에너지 확인 및 지불 → 효과 적용 → 버림 더미 이동**
- 사용 실패(에너지 부족, 잘못된 손패 번호, 대상 없는 공격, 미구현 카드)이면 에너지도 카드도 그대로
- **Buff / Special 카드는 효과 구현 전까지 사용 실패 처리.** 에너지 차감 없음, 버림 더미 이동 없음, 로그: "아직 구현되지 않은 카드 효과입니다."
- 모든 카드는 사용 후 버림 더미로 간다. **카드 소멸 시스템은 MVP에 없다**(추후 확장).

### 4-2. 덱·더미 규칙 `[구현·통과]`
- 전투 시작 시: 런 덱 전체 → 뽑기 더미 → 셔플 → 손패 초기화 → 버림 더미 초기화 (전투마다 새로 섞음)
- 드로우 중 뽑기 더미가 비면 버림 더미를 **즉시 셔플해 새 뽑기 더미**로 만들고 드로우를 이어감. 두 더미가 모두 비면 드로우 중단
- 손패가 10장이면 추가 드로우 카드는 **뽑기 더미에서 소모되어 즉시 버림 더미로** 이동 (슬레이 더 스파이어 방식). 같은 드로우 과정에서 재셔플로 되돌아오지 않고, 다음 드로우부터는 일반 카드로 취급
- 시작 덱 10장: **공격 5, 방어 4, 특수 1**

### 4-3. 카드 강화 `[구현·대기]`
- 구조: `CardData`(원본 에셋) / `CardInstance`(덱에 있는 카드 한 장의 상태)
- 같은 카드가 여러 장이어도 **한 장만** 강화 가능. 카드 한 장당 강화는 **1회**
- 강화 수치는 **카드마다 개별 설정**(`upgradedValue`). **강화 가능 판정 = `upgradedValue > value`** (강화가 없는 카드는 `upgradedValue`를 `value`와 같게 둠)
- **강화해도 비용은 변하지 않는다.** 강화는 기본 수치만 올린다.
- **원본 `CardData` 에셋은 절대 수정하지 않는다.**
- 강화 상태는 현재 런 동안 유지(전투를 넘어서 유지)되고, 새 런 시작 시 초기화
- 강화는 **휴식 노드**에서 "체력 회복 vs 카드 강화" 중 하나를 선택하는 방식. **MVP에서는 상점에서 카드 강화를 제공하지 않는다.**
- 덱 구조: `startingDeck`(인스펙터의 기본 덱 구성) + `runDeck`(현재 런의 `CardInstance` 목록). 새 런을 시작하면 `startingDeck` 기준으로 `runDeck`을 재생성. 런 시작 진입점은 `CombatManager.StartRun()`
- 테스트용 강화 수치(임시, 최종 밸런스 아님): 타격 6→9, 수비 5→8, 강타 10→14, 속공 2→4

### 4-4. 시작 덱의 특수 카드 `[확정·미구현]` (효과는 Phase 4)
- 이름: **재정렬** / 종류: Special / 비용: 1
- 기본 효과: **카드 2장 드로우**, 강화 효과: **카드 3장 드로우**, 강화 시 비용 변화 없음
- 손패 최대 10장, 뽑기 더미 소진 시 재셔플 규칙은 기존과 동일
- 구현 방식: 카드의 `value`를 드로우 장수로 사용 (기본 2, `upgradedValue` 3). 효과 구현 전까지는 사용 실패 처리(4-1)

## 5. 적 규칙

### 5-1. 행동 예고와 순서 `[구현·통과]`
- 적마다 고유 행동 패턴을 가지며 순서대로 반복(순환)
- 일반 적: 다음 행동 1개 예고 / 엘리트: 다음 행동 및 특수 조건 예고 / 보스: 여러 턴 행동 패턴 예고
- **예고와 실제 실행은 항상 일치**해야 한다 (같은 데이터를 사용)
- 적 행동 순서: 화면 왼쪽부터 오른쪽. **UI가 없는 동안은 리스트 순서 = 왼쪽부터**이며, UI 구현 후에도 이 순서를 유지한다.
- 적 회복은 최대 체력을 초과할 수 없다.

### 5-2. 적 행동 종류
- 현재 구현: **Attack, Defend** `[구현·통과]`
- 확정(미구현, Phase 4): **Attack / Defend / SelfBuff / AllyBuff / AllyHeal** 5종 `[확정·미구현]`
  - 아군 강화·회복은 **자신을 제외한 살아 있는 적 중 하나**를 대상으로 한다. **대상이 없으면 그 행동을 건너뛴다.**
  - 대상을 "하나" 고르는 기준(무작위/리스트 순서)과 SelfBuff·AllyBuff·AllyHeal의 구체 효과·수치는 `[미결]`

## 6. 버프·디버프 `[확정·미구현]` (Phase 4)

초기 MVP 효과 4종: **공격력 증가 / 공격력 감소 / 방어도 증가 / 방어도 감소**

- 최종 피해량 = **Max(0, 기본 피해량 + 공격력 보정)**
- 최종 방어도 = **Max(0, 기본 방어도 + 방어도 보정)**
- 플레이어와 적 모두 같은 계산 규칙을 적용한다.
- 지속시간은 턴 단위. **플레이어 효과: 플레이어 턴 종료 시 감소 / 적 효과: 해당 적의 행동 종료 시 감소**
- 같은 효과를 다시 적용하면 **수치는 중첩하지 않고 지속시간만 갱신**
- 반대 효과(증가/감소)는 독립적으로 유지하고 최종 계산에서 합산
- 지속시간이 0이 되면 제거. 최종 능력치는 최소 0. 전투 종료 시 임시 효과 제거
- 초기 테스트 수치: 효과 ±2, 지속시간 2턴. **인스펙터에서 변경 가능**하게 한다.

## 7. 공격 대상 선택 `[확정·미구현]` (Phase 3)

- 단일 공격: 플레이어가 적을 **직접 선택**
- 전체 공격: 모든 살아 있는 적에게 적용
- 무작위 공격: 살아 있는 적 중 무작위 선택
- **방어 및 강화 카드는 기본적으로 플레이어 자신에게 적용**
- `[임시]` 현재 구현은 공격 카드가 "살아 있는 적 중 리스트 맨 앞의 적"을 자동으로 공격한다. Phase 3에서 교체.

## 8. 로그라이크 진행 (명세, 대부분 미구현)

- 3개 구역 + 최종 보스. 각 구역은 분기형 맵, 구역 마지막에 구역 보스
- 노드 종류: 일반 전투, 엘리트, 상점, 휴식, 이벤트, 보스
- **런 종료 시 초기화**: 체력, 골드, 카드, 유물, 임시 강화 / **유지**: 도감·영구 콘텐츠 해금 기록
- 영구 능력치 강화 시스템은 없다.
- 영구 데이터와 런 단위 데이터는 반드시 분리한다. (영구 저장 시스템은 미구현)

### 보상 (Phase 5)
- 전투 승리 후 **카드 보상 또는 골드 보상 중 하나** 선택
- 카드 보상: 무작위 카드 3장 중 1장 선택. 등급 확률 **일반 70% / 희귀 25% / 전설 5%**
- 카드 풀 구성, 골드 획득량, 상점 가격, **보상 건너뛰기 여부는 Phase 5 진입 전에 다시 결정** `[미결]`

### 상점
- 카드 구매, 유물 구매, 카드 제거(현재 런에서 복구 불가). 구매한 상품은 상점에서 제거, 퇴장 후 재방문 불가, 골드 부족 시 구매 불가

## 9. 스킬·유물 (명세, 미구현)

- 스킬: 별도 슬롯에 장착, **초기 슬롯 2개**, 카드와 같은 에너지 사용, 에너지가 충분하면 반복 사용 가능, 전투 중 교체 불가, 전투 승리 후 장착·교체 가능. 스킬은 보스·이벤트·특수 조건으로 획득. 영구 해금 스킬은 이후 런에서 획득 후보가 될 수 있음
- 유물: 패시브 중심, 보유 개수 제한 없음, 기본적으로 독립 작동, 일부 핵심 조합에만 시너지, 보스 처치 시 보스 전용 유물 1개 확정 획득, 런 종료 시 초기화, 도감 발견 기록은 영구 유지

## 10. 장기 방향 (UI·수학 시스템·도감)

- **UI**: Phase 1~2에서는 보류(Debug.Log와 인스펙터). 전투 시스템이 안정되면 실제 화면 구현 예정 — 플레이어 체력·에너지 표시, 적 캐릭터와 체력 표시, 손패 카드 표시와 클릭으로 사용, 적 클릭으로 대상 선택, 턴 종료 버튼, 카드 효과·전투 상황 표시, 승리·패배 화면. 이후 메인 메뉴, 분기형 맵, 상점, 휴식, 유물, 도감 UI
- **UI 설계 원칙**: UI는 게임 로직의 함수를 호출하고 공개된 상태를 읽기만 한다. 로직은 UI를 알지 못한다.
- **수학 시스템**: 카드 데이터에 나중에 연결할 수 있도록 구조를 고려한다 — 수학적 분류(사칙연산·방정식·함수 등), 수학 기호·공식 표현, 카드의 실제 전투 효과, 카드 설명과 수학적 원리, 도감 등록 연결, 카드 강화와 수학적 효과의 관계. **복잡한 범용 효과 시스템을 미리 만들지 않고**, 실제 구현 단계에서 필요한 만큼 확장한다.
- **도감**: 획득한 수학 공식·기호를 확인하는 선택형 보조 시스템. 신규 공식 획득 시 등록, 간단한 설명과 활용법 제공, 전투 중에는 간략 설명 + "자세히 보기"로 도감 이동. **도감을 읽지 않아도 클리어 가능**해야 한다. 독립형(메인 메뉴/마을)과 전투 연동형을 섞은 A+B 방식
- 이후 Phase 계획에 **UI 프로토타입과 수학 공식 시스템을 반드시 포함**한다.
